# `bestie.framework.orm`

Database abstraction framework for typed persistence and query workflows.

## Purpose

`orm` provides structured mapping between domain models and relational data while preserving explicit query intent and transaction boundaries.

It aims to reduce boilerplate around:

- Entity persistence
- Query construction
- Transaction management
- Repository organization

## Layering and Dependencies

`orm` is part of `std-framework` and builds on:

- `bestie.api.db`
- `bestie.api.io` (optional for migration scripts)
- `bestie.lib.utilities` / `bestie.lib.collections`

Import style:

```bestie
import bestie.framework.orm
```

## Core Concepts

- `Entity`: persistence-aware domain type, declared with `@Entity`.
- `Repository`: typed data access interface.
- `Session`: unit of interaction with the DB backend.
- `Transaction`: explicit boundary for consistent writes.
- `Query`: composable and typed query object.

## Annotation-Driven Mapping

Entity mapping is declared through annotations. The compiler validates the schema metadata and generates serialization/deserialization code at compile time — no runtime reflection.

### Entity Annotations

| Annotation | Target | Effect |
|---|---|---|
| `@Entity` | class | Marks as a persistence-mapped type |
| `@Table(name)` | class | Maps to a specific table name (defaults to class name) |
| `@Column(name?)` | field | Maps field to a column; name defaults to field name |
| `@Id` | field | Declares the primary key |
| `@GeneratedId` | field | Primary key is generated by the database |
| `@Nullable` | field | Column allows NULL; field type must be optional |

### Relationship Annotations

| Annotation | Target | Effect |
|---|---|---|
| `@ManyToOne(foreign_key)` | field | Many-to-one association |
| `@OneToMany(mapped_by)` | field | One-to-many association; lazy by default |
| `@OneToOne(foreign_key)` | field | One-to-one association |
| `@Eager` | field | Forces eager loading on a relationship |

### Example Entity

```bestie
import bestie.framework.orm

@Entity
@Table("users")
class User {
    @Id @GeneratedId
    val id: int

    @Column("email")
    val email: str

    @Column
    val createdAt: DateTime

    @ManyToOne("team_id")
    val team: Team
}

@Entity
@Table("teams")
class Team {
    @Id @GeneratedId
    val id: int

    @Column
    val name: str

    @OneToMany(mapped_by = "team")
    @Eager
    val members: List<User>
}
```

## Repository Pattern

```bestie
import bestie.framework.orm

protocol UserRepository : orm::Repository<User, int> {
    fun findByEmail(email: str) -> User?
    fun listByTeam(teamId: int) -> List<User>
}
```

The `orm` framework generates a default implementation. Custom query methods can be backed by typed query builders or inline SQL.

## Transaction Model

- Transactions are explicit (`begin`, `commit`, `rollback`).
- Nested transactions use savepoints when supported by the driver.
- Auto-commit behavior must be opt-in.

```bestie
import bestie.framework.orm

fun createUser(repo: UserRepository, email: str) {
    orm::transaction(fun(tx) {
        repo.insert(User { email: email, createdAt: DateTime.now() }, tx)
    })
}
```

## Query Builder

```bestie
import bestie.framework.orm

fun activeUsersInTeam(session: orm::Session, teamId: int) -> List<User> {
    return session.query<User>()
        .where(User::team.id == teamId)
        .orderBy(User::createdAt, desc)
        .limit(50)
        .fetch()
}
```

Queries are typed and validated against entity metadata at compile time where possible.

## Non-Goals

- No runtime schema guessing via reflection
- No hidden write flush at arbitrary points
- No bypass of explicit transaction semantics
